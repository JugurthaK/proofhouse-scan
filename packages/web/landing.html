The problem

Your scanners found 42 issues. How many are actually real?

Static analysis flags a SQL string in a test fixture. A secret scanner flags the placeholder key in your docs. The real vulnerabilities hide in the noise, and sorting them by hand eats the afternoon.

How it works

From raw findings to merged fixes.

Three steps, all driven from one dashboard or the command line. Nothing to install in the repositories you scan.

  1. 1

    Scan any GitHub repository.

    Point it at owner/repo. The scan runs in GitHub Actions with three proven open-source scanners, and every result lands deduplicated in one database.

    • Opengrep finds vulnerable code patterns (SAST).
    • Trivy checks dependencies for known CVEs and infrastructure-as-code for misconfigurations.
    • Gitleaks hunts for secrets across the full git history, not just the latest commit.

  2. 2

    Let an LLM sort the real from the noise.

    One click sends a finding and the code around it to Claude or an OpenAI model. You get a verdict, a confidence score and the reasoning behind it, plus an exploit scenario for the ones that are real.

    • True positive, false positive or needs review: never a silent dismissal.
    • Verdicts stick to the finding and survive every re-scan.

  3. 3

    Ship the fix as a pull request.

    For confirmed issues, the LLM writes a minimal patch. Proofhouse Scan pushes a branch and opens a pull request on the target repository, from a fork if you don’t have write access. You review, you merge.

    • See the diff in the dashboard before anything is pushed.
    • Re-scan after merging and the finding moves to resolved.

And there’s more

Built for how small teams ship.

Secrets in git history

Gitleaks scans every past commit, so a key deleted last year still turns up.

Smart re-scans

Fingerprinted findings move from new to open to resolved, and reopen if they come back.

Runs in your CI

A drop-in GitHub Action scans on every push and sends results to your instance.

Quality gate

Fail the build when a push adds new findings at or above the severity you choose.

GitHub sign-in

Restrict the dashboard to an allowlist of GitHub users or organizations.

CLI and web UI

Script scans and triage from the terminal, or click through dashboards in the browser.

Two ways to scan

From your terminal, or from your CI.

Pick one per repository. Either way, findings land in the same dashboard.

Central dispatch

The scan workflow lives in your Proofhouse Scan repository. Target repositories stay untouched.

zsh 
$ pnpm proofhouse-scan scan acme/payments-api
  Dispatched scan.yml, waiting for the run…
  ✓ opengrep: 14 findings
  ✓ trivy: 23 findings
  ✓ gitleaks: 5 findings

GitHub Action

Run the same scanners on every push and fail the job on new high-severity findings.

.github/workflows/proofhouse-scan.yml 
steps:
  - uses: actions/checkout@v7
    with:
      fetch-depth: 0
  - uses: JugurthaK/proofhouse-scan/action@v1
    with:
      api_url: https://your-instance.example.com
      api_token: ${{ secrets.PROOFHOUSE_SCAN_INGEST_TOKEN }}
      fail_on: high

Good to know

Is it right for you?

No surprises. Here is what Proofhouse Scan is, and what it isn’t.

Self-hosted, not a SaaS

You run it: one container and a SQLite file. Your code and findings stay with you.

Made for small teams

One instance on one machine, no horizontal scaling. Built for teams shipping their own apps.

GitHub only

Scans run on GitHub Actions and fixes open as GitHub pull requests. No GitLab or Bitbucket.

Bring your own LLM key

Triage and fixes use your own Anthropic or OpenAI account. Scanning works without one.

Self-host

Up and running in minutes.

Clone, build, scan. Or ship the whole thing as one Docker container with a volume for the database.
